3Description

ARK-3 is a complete, reproducible ad-ranking stack built on a sample of the Criteo click logs. A DeepFM ranker models second-order and deep feature interactions over every embedded field. A two-tower model, trained to imitate that ranker, maps contexts and ads into one vector space so FAISS can shortlist candidates; DeepFM then re-scores only the shortlist.

The ranker is exported to ONNX and served from a C++ harness built on ONNX Runtime, where thread placement and buffer reuse are tuned against a fixed request shape: one context × a shortlist of candidates.

5Detailed Description

5.1Overview

A request arrives with a context (the context pins). Stage one encodes it with the query tower; stage two asks a FAISS IVF index for the catalog items with the highest tower score; stage three runs DeepFM on exactly those pairs and returns the top ads by predicted click probability. An offline benchmark compares that output against an oracle that runs DeepFM on every catalog item, which shows how small the shortlist can be.

5.3Feature Description

5.3.1 Field Encoding

Count features (I1–I13) are discretised: small values keep their own bucket, larger values map to ⌊ln²(x)⌋, the transform used by the winning Kaggle Criteo solutions. Categorical features (C1–C26) get a vocabulary fit on the training split only, with rare values sharing an out-of-vocabulary row and missing values their own row. Every field then indexes one shared embedding table; per-field offsets live inside the model so the exported graph consumes the raw int64[B, 39] tensor.

5.3.2 DeepFM Ranker

DeepFM (Guo et al., 2017) sums three terms that read the same field embeddings: a first-order linear term, the factorisation-machine pairwise term ½[(Σv)² − Σv²], and a deep MLP with batch norm and dropout. Training uses Adam, evaluates on validation several times per epoch, decays the learning rate whenever validation stops improving, and stops early. Embedding L2 is chosen per configuration on validation log loss, and the same protocol trains the LR, FM and DNN ablations.

5.3.3 Ad / Context Split

Retrieval needs an item side, but Criteo's fields are anonymous. Attributes of one entity are functionally dependent, so for every pair of categorical fields the pipeline computes the normalised conditional entropy U(J|K) = H(J|K)/H(J). High-cardinality fields that pin down several others are candidate ad keys. Each candidate catalog is then scored by the trained DeepFM, and the entity whose ranking depends most on the query is kept: , carrying . The catalog is the most frequent keys, each with its modal attributes.

5.3.4 Two-Tower Retrieval, Distilled from the Ranker

Both towers embed their fields and pass them through an MLP to unit-norm vectors. A click-trained tower (in-batch sampled softmax with logQ correction) learns what gets clicked, but the funnel must find what DeepFM will rank highest. The distilled tower therefore minimises KL(teacher ‖ student) between the softmax of DeepFM logits and of tower scores over slates of uniformly sampled items plus the student's own current top items (hard negatives). Each item also learns a scalar bias stored as an extra vector coordinate (the query appends a constant 1), so inner-product search in FAISS reproduces the tower score exactly.

5.3.5 FAISS Candidate Recall

Item vectors go into an IndexIVFFlat inverted-file index. The number of probed lists scales with the requested shortlist size, so larger budgets scan proportionally more of the catalog.

5.3.6 ONNX Export and C++ Harness

The ranker is exported with a dynamic batch dimension and the sigmoid in-graph, then verified against PyTorch on held-out rows. cpp/bench.cpp replays real fine-ranking requests through ONNX Runtime and reports latency percentiles for each serving configuration.

      6.2Layout Guidelines

      • Size the shortlist from the offline budget sweep, not from habit.
      • Retrieval quality is bounded by agreement with the ranker, not by how well it predicts clicks — distil the ranker into the retriever.
      • On CPU, pick intra-op threads from the sweep instead of defaulting to the core count, and keep request buffers alive across calls.
